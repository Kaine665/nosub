## 1. 字幕读取(目标 A)

### 1.1 可行路径:已确认

YouTube 的 `POST https://www.youtube.com/youtubei/v1/get_transcript` 端点能返回完整 cue。
LZArpRwziE8 实测拿到 **1127 条**毫秒精度的 cue。

### 1.2 实现架构:方案 B(全字段复刻 INNERTUBE_CONTEXT)

**关键事实**:手动拼最小 `context`(只带 `clientName`/`clientVersion`)会 400 `FAILED_PRECONDITION`。
YouTube 服务端校验 32 个 client 字段,关键必需项至少包括 `visitorData`(会话级令牌)和 `remoteHost`(出口 IP)。

**实现策略**:不挑字段,**直接复刻页面全局 `yt.config_.INNERTUBE_CONTEXT` 整个对象**作为请求的 `context`。
- 优势:YouTube 改字段我们自动跟随,最稳、最少维护
- 扩展运行环境(content script + YouTube host permission)天然带 cookie,`credentials: 'include'` 即可

**请求模板**:
```js
fetch('https://www.youtube.com/youtubei/v1/get_transcript?key=' + yt.config_.INNERTUBE_API_KEY, {
  method: 'POST',
  credentials: 'include',
  headers: { 'content-type': 'application/json' },
  body: JSON.stringify({
    context: yt.config_.INNERTUBE_CONTEXT,   // 整个对象, 不挑字段
    params: <token>,                          // 从 ytInitialData 取
    languageCode: 'en',                       // 从 track 取
    kind: 'asr' | undefined,                  // 从 track 取
    externalVideoId: <videoId>,
  }),
});
```

**params token 的来源**:
- 路径:`window.ytInitialData.engagementPanels[].engagementPanelSectionListRenderer.content.continuationItemRenderer.continuationEndpoint.getTranscriptEndpoint.params`
- 这是**唯一正确的字段名**(探针曾遍历 14 个候选 token,只有 `getTranscriptEndpoint.params` 这条路径是对的)
- token 是 URL 编码的,直接传即可(fetch 会处理)

### 1.3 响应结构(实测,纠正了原假设)

**原假设错误**:cue 在 `actions[].reloadContinuationItemsCommand.continuationItems[]`。
**实际路径**:
```
actions[0].updateEngagementPanelAction
  .content.transcriptRenderer
  .content.transcriptSearchPanelRenderer
  .body.transcriptSegmentListRenderer
  .initialSegments[]
  .transcriptSegmentRenderer
```

每个 `transcriptSegmentRenderer` 含:
- `startMs`(字符串,毫秒)
- `endMs`(字符串,毫秒)
- `snippet.runs[].text`(拼接得 cue 文本)

**实现建议**:解析器主走这条路径,但保留对 `reloadContinuationItemsCommand` 路径的兜底(以防 YouTube 不同上下文返回不同结构)。

### 1.4 字幕轨道发现(目标 A 的前置)

**主路径**:`window.ytInitialPlayerResponse.captions.playerCaptionsTracklistRenderer.captionTracks`
- 直接读页面全局,0ms,无需请求
- 每条 track 含 `languageCode`、`kind`、`name.simpleText`、`baseUrl`

**兜底路径**:POST `youtubei/v1/player`(ANDROID client)—— 1.0 不必实现,主路径足够。

### 1.5 人工字幕 vs ASR 判别(已确认)

TED 视频实测两种英文轨道并存:
```
{ kind: undefined,    name: '英语' }              ← 人工
{ kind: 'asr',        name: '英语 (自动生成)' }   ← ASR
```

**规则**:`track.kind === 'asr'` → ASR;否则 → 人工。
映射到 design §4 的 `CaptionTrack.isAutoGenerated = (track.kind === 'asr')`。

**track 选择策略**(spec 未明确,实现决策):同一语言优先人工 > ASR(人工更准、断句更干净)。

### 1.6 失败/放弃的路径(记录,避免重复踩)

| 路径 | 现象 | 原因 |
|---|---|---|
| `timedtext` baseUrl 直接 fetch | HTTP 200/204, bodyLen=0 | YouTube 2024+ 要求 PO Token,单靠 signature/key=yt8 不够 |
| `get_transcript` 手拼最小 context | 400 FAILED_PRECONDITION | 缺 visitorData/remoteHost 等字段 |
| `Request.clone()` 读 body | `Request body is already used` | YouTube 已消费 body |
| `init.body` 直读 | 拿到的是 gzip 字节,TextDecoder 解码破坏数据 | gzip 字节不是合法 UTF-8 |

**最终成功的拦截法**:包装 `window.Request` 构造器,在 YouTube 创建 Request 瞬间从 `init.body` 拿原始字节(Uint8Array),用 `DecompressionStream('gzip')` 解压。这条仅用于探针;扩展里走方案 B 不需要拦截。

## 2. 循环控制(目标 B)

### 2.1 rAF 轮询精度(已验证)

LZArpRwziE8 第 2 条 cue(6.879s-13.120s)实测循环 10 轮:

```
循环间隔(ms): [6341, 6342, 6341, 6334, 6341, 6342, 6342, 6347, 6353]
平均超调: 5.6ms
间隔标准差: 5.1ms
seek 耗时: 0.1-1.0ms
```

**结论**:**0 累积漂移**(标准差 5ms),超调远低于人耳感知阈值(~50ms)。
seek 耗时亚毫秒,可忽略。

design §5.4 的"绝对起点重算,不累加时间差"策略被验证正确。

### 2.2 用户 seek vs 插件 seek(关键发现:无法区分)

实测两组事件序列**完全一致**:
```
插件 seek:  play → seeking → seeked
用户拖动:   play → seeking → seeked
```
事件类型、顺序、`paused` 状态、currentTime 跳变模式——**无一可区分**。

**结论**:**不能靠事件区分两者**。design §5.1 的 `pendingInternalSeek` 标记是**唯一可行方案**:

```
插件自己 seek 前 → 设 pendingInternalSeek = {targetMs, expiresAtMs}
收到 seeked →
  若在窗口内 且 currentTime 接近 targetMs → 视为插件 seek,忽略
  否则 → 视为用户主动 seek,退出循环
窗口过期 → 清除
```

这是探针最有价值的产出之一——把一个"看似能靠事件区分"的设想否掉了,逼出了正确实现。不测就写,一定 bug。

### 2.3 容差参数(design §5.4)

- `END_TOLERANCE_MS = 60`(实测平均超调 5.6ms,60ms 留 10 倍余量)
- `START_OFFSET_MS = 10`(seek 回起点时加 10ms,避免落在上一 cue 边界)

**注**:这两个参数基于 6.3 秒的 cue 测得。极短 cue 行为未测,留待 T21 回归校准。

## 3. 未覆盖范围(1.0 明确不测)

以下情况 1.0 **不预先适配**,等真实用户反馈 bug 再说:

- 无字幕视频(spec §9 异常处理:检测到就提示"换视频",不补救)
- 年龄限制、会员、地区限制视频
- 直播、Shorts
- 极短 cue(< 1 秒)的循环抖动
- 翻译字幕轨道(依赖 design §6.2 的后续探针,T18 再处理)

**判别条件**:无字幕视频的精确检测方式**探针未确认**(C2 测试用了错视频)。
实现时的临时判别:`captionTracks` 为空数组或不存在 → 提示无字幕。如 T21 回归发现误判,再细化。
